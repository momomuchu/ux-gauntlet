### BLOCKER

#### F10 mandates one friction instance per off-path action; F136/F159 presuppose within-persona re-encounter consolidation into ONE instance — no requirement bridges them, so frequency>1 is architecturally unreachable
**IDs:** F10, F136, F159, F12, requirements.txt:17, requirements.txt:196, requirements.txt:242, spec.md:186
**Failure story:** A literal F10 implementation creates a fresh friction-instance object on every repeated off-path action instead of incrementing a re-encounter counter, because no requirement operationalizes within-persona consolidation (F45/F46's dedup is orchestrator-level, post-hoc, over findings.json — not the persona's own action stream). This makes F136/F159's frequency-bucket mechanism unreachable in practice: frequency collapses to 1 for every off-path friction, and no acceptance fixture derives frequency from a raw per-action ledger, so the gap is never exercised by the frozen suite.
**Fix directive:** Add a new requirement line to .swe-spec/requirements.txt (after F136, e.g. as F136a or next free F-number) reading exactly: "F210: A persona subagent MUST NOT record a new friction instance when an action's (heuristic_tag, step, target_element_identifier) tuple matches a friction instance already recorded earlier in its own run; the persona subagent MUST instead increment that instance's raw_within_run_reencounter_count field, which F159/F162 bucket into the frequency and persistence factors." Then add one test to test/acceptance.test.mjs plus one fixture representing a raw per-action event ledger (not a hand-typed severity_factors object) — the test must run the ledger through the actual consolidation logic (or a documented reference implementation) and assert the resulting friction instance has raw_within_run_reencounter_count=N (not N separate instance objects), proving F10 and F136 are reconciled rather than merely both gate-checked independently.

#### ADR-0001 exit-code table is self-contradictory: "missing required flag" is bucketed at BOTH exit 1 and exit 2 in the same paragraph
**IDs:** ADR-0001 lines 38-45, F107, F108, F61, F65
**Failure story:** ADR-0001 lines 38-40 bucket every missing-required-flag case (missing --url/--tasks/--i-own-this-target/--env/--denylist) under exit 1 (refusal to start), then two sentences later line 44-45 defines exit 2 (usage error) as covering "unknown flag, missing required flag, a --max-parallel value below 2" — reusing the literal phrase "missing required flag" for the opposite exit code. A builder implementing conventional argv parsing (absent flag → usage error) would route these to exit 2, contradicting F107/F108 and failing 5+ frozen tests that hard-assert exit code 1 for missing required flags.
**Fix directive:** In docs/adr/0001-runner-cli-contract.md line 45, change the exit-2 definition from "`2` = usage error (unknown flag, missing required flag, a `--max-parallel` value below 2 per F185);" to "`2` = usage error (unknown flag, a `--max-parallel` value below 2 per F185 — never an absent required flag, which is always the exit-1 refusal defined above per F107/F108);". No requirements.txt change needed (F107/F108/F185 wording is already correct and consistent); this is purely an ADR prose fix removing the stray duplicate phrase.

**Fix directive:** In docs/adr/0001-runner-cli-contract.md, amend the `--help` table row (line 34) to add explicit precedence language, e.g.: "`--help` | no | prints usage text and exits 0, checked before any F107/F108 static launch precondition — always short-circuits regardless of which/how many required flags are present or absent; per F152, MUST reference `--override-robots`...". Add a companion negative-control requirement/test proving --help still wins when invoked alongside a fully-violating flag set (acceptance.test.mjs:848 already covers the all-missing case) — add a second assertion, or a new test, invoking --help together with an otherwise-complete valid invocation, asserting exit code 0 and stdout matches /override-robots/i, to remove any doubt that --help precedence is independent of flag completeness in either direction.

## 3. REJECTED attacks

- **denylist_override can never co-occur with an F40 dry-run exemption, so the "legitimately audited destructive flow" scenario is unbuildable** — rejected: the cited scenario's Then-clauses never require the request to submit or reference F40/dry-run at all; the frozen fixture/test model it as satisfied via the click-vs-abort mechanism alone, and D15's design already assumes destructive multi-step flows are decomposed across precondition_step + audited_terminal_step, which the scenario doesn't rule out.
- **D15's decision-table prose scopes audited_terminal_step to "ONLY the audited task's own FINAL non-idempotent submission," risking under-implementation of multi-submission happy paths** — rejected: F126/F127's precondition_step flag (unconditionally worded, no positional restriction) already covers the non-terminal submission role the attack claims is unreachable, and F164's mutual-exclusivity rule doesn't block using both flags on different steps in the same task list.
- **N8's "zero failed prior attempts" guarantee is textually scoped to localhost only, silently excluding the staging-target first run** — rejected: the scoping is explicit and stated twice verbatim ("against a reachable localhost target"), not buried; the attack's own framing concedes the exclusion is textual, undercutting its claim of reasonable operator confusion, and D15/F67/F68 separately and clearly name the non-localhost gate as a distinct requirement.

## 4. Systemic observations

- All 3 BLOCKER-severity confirmations landed in mechanical/procedural territory (within-persona frequency-consolidation architecture, the CLI exit-code table, `--help` precedence) rather than in the domain severity-scoring rubric — the panel's teeth bit hardest on operational/CLI-contract gaps this round, not on friction-scoring semantics.
- Two independently-run attacks converged on the identical defect (F206 citing F147 for terminal_friction step non-recurrence, which F147 explicitly excludes) and were scored MAJOR and MINOR respectively by different verification passes, with overlapping but non-identical fix_directives targeting the same requirements.txt:378 line. Both are reported as separately confirmed per this round's input, but they should be reconciled into one fix before implementation to avoid conflicting edits to the same line.
- Recurring pattern: multiple confirmed defects are stale/contradictory cross-references left behind when a later CR (D15, CR3-1, CR6-B2, CR7-4) superseded an earlier claim without a full-document reconciliation pass (spec.md:249 vs :201; F206's F147 citation vs CR7-4). Suggests challenge rounds are finding new defects faster than a systematic "does this later decision's claim get echoed correctly everywhere else in the document" sweep is being run.
- Severity-assessment discipline is visibly functioning, not rubber-stamped: 3 of this round's attacks arrived with BLOCKER-level severity_claim framing (F179/F180 fail-open, F161 impact-factor grounding, `--personas` extension filter) and were downgraded to MINOR on verification against canonical spec.md paragraphs and frozen fixtures — evidence the confirm/reject bar is checking actual files, not accepting dramatic framing at face value.
- market_impact (F13/F209) is the single weakest-specified field in the ruleset this round: 2 independent confirmed defects (no default-value clause for the non-triggered case; no merge rule across F46 dedup) both trace back to the same under-specified flag, and a third attack (spec.md overclaiming F209 satisfies the brief's fuller mandate) also targets it — suggests market_impact warrants a dedicated close-out pass rather than three separate point fixes.
- The REJECTED set (3/3 this round) held the line against theatrical readings that ignored adjacent scenario/fixture/requirement text already resolving the claimed ambiguity — the confirm bar is not one-directional.
