#### F165's finding_id hash formula joins (heuristic_tag, step, target_element_identifier) with an unescaped "|" delimiter, letting real-world accessible-name text collide two genuinely distinct findings into one hash
**IDs:** F165, F103, F45, F92
**Failure story:** F165's formula is sha256(`${heuristic_tag}|${step}|${target_element_identifier}`) with no escaping; F103's tier-2 target_element_identifier fallback (accessible-name-plus-role) is derived from arbitrary third-party site text an operator does not control, and real UI text commonly contains literal "|" characters (mega-menus, split-action buttons). **Fix directive:** In .swe-spec/requirements.txt, amend F165 (line 249) to specify an unambiguous encoding before the join, e.g.: replace the literal-string formula with 'fid-' + first 16 hex chars of sha256 of the three components each percent-encoded (encodeURIComponent) then joined with '|', i.e. sha256(`${encodeURIComponent(heuristic_tag)}|${encodeURIComponent(step)}|${encodeURIComponent(target_element_identifier)}`). State explicitly that this prevents a '|' character inside any component from being interpreted as a field boundary. Then in test/acceptance.test.mjs, add a fixture pair adjacent to the existing F165 test (near line 413-424): one finding with target_element_identifier containing a literal '|' and a sibling with the field boundary shifted; assert their finding_ids differ. Add a positive control asserting two personas hitting the identical pipe-containing element still produce matching finding_ids (merge behavior preserved).

#### Severity formula's frequency/persistence duplication is disclosed as a mathematical fact but not as its downstream triage consequence — a total-task-abandonment finding can rank below a trivial recurring nuisance
**IDs:** F12, F159, F161, F162, F181, requirements.txt:19, requirements.txt:228, requirements.txt:245-246, requirements.txt:281, DECISION-BRIEF.md:39

The arithmetic double-counting is already disclosed and was already arbitrated (CR6, out-of-scope-at-spec-phase), but the disclosure text (F181) never states the downstream triage consequence, so a report reader is not warned that severity ordering can invert the one thing severity is for.
**Fix directive:** Do not add an impact floor or change the formula — that was already proposed and explicitly rejected by prior arbitration (scrub-log.md CR6-B4). Instead amend F181 (requirements.txt:281) to close the disclosure-completeness gap by appending one clause stating the downstream consequence, not just the mathematical fact. Suggested amended line: "F181: The validity-envelope disclosure section MUST state that, when severity_factors is stored as 3 numeric values, F162's default persistence bucket equals F159's default frequency bucket for every possible raw within-run re-encounter count, making persistence a deterministic duplicate of frequency rather than an independently verified NN/g input, and MUST additionally state that this duplication weights the frequency factor twice against the impact factor's single weighting, so a single-encounter task-abandoned-or-never-resumed friction (impact=4) can compute a lower severity value than an 11-plus-times-recurring self-recovered friction (impact=0)." Add a corresponding assertion to the F181 disclosure-render test in test/acceptance.test.mjs checking the new clause's literal text is present in the rendered validity-envelope section.
