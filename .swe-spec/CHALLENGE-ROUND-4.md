## 2. CONFIRMED defects

### BLOCKER

#### F53's closed run_status enum has no value for an F57/F58/F99/F100/F154 forced-abort
**IDs:** F53, F57, F58, F99, F100, F154, F56, F123
**Failure story:** F53 closes run_status to exactly {completed, crashed, timed-out, patience-exhausted}, but F57/F58 (50-action cap) and F99/F100/F154 (tool-call cap) force an abort explicitly independent of patience_threshold_steps — a persona hitting the action cap has no enum value it can legally report. The frozen F57/F58/F154 fixtures only prove the negative case (rejecting `completed`); neither has the `-ok` positive-control fixture every sibling terminal-state rule (F75/F76, F55/F56) carries, because no correct value exists to put there.
**Fix directive:** Add a 5th run_status enum member (e.g. 'runner-capped') to F53, and a matching reason code to F123's enumerated set (e.g. 'action-cap-exceeded' / 'tool-call-cap-exceeded', or a single shared code), then re-derive the two F57/F58 and F154 acceptance-test fixtures to add the missing positive-control '-ok.json' pair proving the correct value, matching the existing convention for every other terminal-state rule in the suite.

#### F49's BLOCKED trigger cannot distinguish a genuine execution failure from designed patience-exhaustion
**IDs:** F49, F53, F50, F51, F52, F101, F17
**Failure story:** F49 sets run_status=BLOCKED when fewer than 3 personas complete "due to a persona-execution failure," but F53's flat enum gives no failure/non-failure axis, and F50-F52 define patience-exhaustion as a designed, successful methodology outcome — not a failure. A run where 2 of 3 personas legitimately abandon via patience exhaustion (0 crashed/timed-out) can be read as BLOCKED, making F101 exit CI nonzero on the tool's most valuable output (catching a genuinely terrible flow), indistinguishable from an infra crash.
**Fix directive:** In .swe-spec/requirements.txt, revise F49 to explicitly scope the failure set, e.g.: "F49: The orchestrator MUST record a machine-readable run-status field, separate from findings.json, that is set to BLOCKED when fewer than 3 persona subagents reach run_status completed, crashed, or timed-out — patience-exhausted personas MUST NOT count toward the BLOCKED trigger." Update docs/specs/0001-ux-gauntlet-mvp.spec.md line 187 to match this scoped wording instead of repeating the ambiguous phrase. Add a new fixture (e.g. test/fixtures/run-status-not-blocked-patience-only.json) with 2 patience-exhausted personas + 1 completed persona (0 crashed/timed-out) and run_status != BLOCKED, plus an acceptance.test.mjs assertion that this fixture exits CI clean (code 0), proving patience-exhaustion alone never triggers BLOCKED/CI-red.

#### F12's severity formula is only 1/3 defined — impact and persistence have no scoring rubric
**IDs:** F12, F136, F159, F92, F151, F157
**Failure story:** Only frequency (F136/F159) has a fixed scoring procedure; impact and persistence appear nowhere else in the spec beyond F12's formula sentence, so the "gate-verified" round(mean(...)) check only proves internal arithmetic consistency, not that the inputs mean anything or are reproducible. Since finding_id (F92) deliberately excludes severity, unconstrained impact/persistence judgment alone can flip identical findings from severity <4 to severity 4 across runs, triggering F151's CI hard-block as if it were a real regression.
**Fix directive:** In .swe-spec/requirements.txt, add two new atomic requirement lines immediately after F159 (line 228): F160 defines impact via a fixed mapping over the persona's terminal recovery outcome (self-recovery=0 ... abandoned-and-never-resumed=4), and F161 defines persistence via a fixed mapping over same-run recurrence of the same finding_id (resolved-once-never-recurring=0 ... recurred-5+-times-or-never-resolved=4), each tagged with its own CR marker. Extend F157 (line 226) to remove the free-text-only scoping so the reproducibility caveat covers the numeric branch too. Add fixture-backed gate tests in test/acceptance.test.mjs mirroring the F159 pattern: a bad fixture with an unscoped ad-hoc impact/persistence value not traceable to the F160/F161 mapping, and a good fixture where the mapped category is included in evidence and matches the numeric value.

#### F14/F15's evidence-drop gate test is a single unconditional substring match with no exit-code check and no negative control
**IDs:** F14, F15, test/acceptance.test.mjs:205-209
**Failure story:** The entire proof for this [CRITICAL][BLOCKS:high] rule is `assert.match(r.stdout + r.stderr, /DROPPED/, ...)` — no `.code` assertion, and no `-ok` companion fixture proving a finding WITH evidence survives, breaking the CR2-3 pattern every sibling rule received. A builder can pass by printing a static "DROPPED" legend line on every invocation while never actually filtering zero-evidence findings, letting fabricated findings reach findings.json — exactly what F14/F15 exists to prevent.
**Fix directive:** In test/acceptance.test.mjs, strengthen the existing 'F14 F15' test: (1) add `assert.equal(r.code, 0, ...)` for a run containing one dropped zero-evidence finding alongside other valid findings; (2) add a companion fixture `finding-evidence-present-ok.json` (populated evidence array, otherwise valid) and assert its output does NOT match /DROPPED/ and its findings count is preserved, mirroring the CR2-3 `-ok` companion pattern used for denylist/robots/evidence-redacted/run-status-blocked/walkthrough; (3) using the existing finding-no-evidence.json fixture (fr-001 dropped, fr-002 kept), additionally assert the gate's output still references fr-002 as retained, proving selective dropping, not just presence of the word DROPPED.

## 4. Systemic observations

- **Closed enums and flag families keep shipping without a combinatorial/forced-abort audit.** F53's run_status enum, D15's "CLOSED" 5-flag family, and F49's BLOCKED trigger all failed the same way: a terminal state or flag combination that the architecture can legitimately produce has no defined behavior, because each closure was verified against its intended cases but never against adjacent runner-level or flag-vs-flag interactions.
- **A scoring-formula fix applied to one factor was never generalized to its siblings.** F136/F159 fixed frequency's reproducibility gap two rounds ago; impact and persistence — named in the same F12 formula — never got the same treatment, and F157's caveat was scoped only to the free-text path, leaving the "authoritative" numeric path just as unreproducible for 2 of 3 inputs. The same shape recurs in F150's undefined config-file designation field.
- **Negative-control test coverage is uneven across otherwise-similar gates.** CR2-3 established the "-ok fixture per rule" convention project-wide, but F14/F15 (a CRITICAL anti-fabrication gate) and F9's core 4-question mandate never received it — both can be satisfied by literal string-printing rather than real behavior.
- **Downstream summary docs drift from requirements.txt as the actual SSOT.** README's freeze-readiness table is stale by a full challenge round (169 vs. claimed 153 requirements) — the same class of drift as F24's stale literal "Nielsen" wording surviving after F11/F28/D7 had already generalized.
- **Pluggability commitments (D7) regress to hardcoded defaults in enforcement-layer wording even when adjacent requirements and tests already generalize correctly** — F24 is the clearest instance; worth a pass checking every CRITICAL gate requirement's literal wording against its own paired decision record.
