### BLOCKER

#### F43/F44's "Bearer/JWT token" redaction pattern is the one credential-shape left with zero normative regex, unlike every sibling pattern
**IDs:** F43, F44, spec.md:203, test/acceptance.test.mjs:772-818, test/fixtures/evidence-secret-leak.json
**Failure story:** Every sibling redaction class (cookie, API-key, card-number) received a literal, testable shape definition after being challenged in earlier rounds, but "Bearer/JWT token" never did — it remains unqualified prose, and all four fixtures exercising this clause hardcode the same JWT-dot-structured literal. A builder implementing strictly from the requirement text and that fixture will plausibly ship a JWT-only regex that lets every real-world opaque OAuth2/session bearer token (the common shape) flow straight to committed evidence artifacts unredacted — the exact DR-05 credential-leak scenario this requirement exists to prevent.
**Fix directive:** 1) Split F43/F44 in .swe-spec/requirements.txt into a shape-qualified Bearer clause and a standalone JWT clause, mirroring the CR3-8/CR4-M4 treatment already given to the API-key and cookie clauses: replace "a Bearer/JWT token" with "a case-insensitive `Bearer ` (Authorization scheme) prefix followed by a run of 20+ URL-safe-base64/hex token characters (covers opaque OAuth2/session tokens and JWTs alike), OR a standalone three-dot-separated base64url JWT (`eyJ[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+`) appearing without an Authorization: wrapper (e.g. in a URL query string or localStorage dump)". 2) Add matching normative text to spec.md:203's redaction-pattern-set sentence, in the same style as the existing cookie-clause shape definition. 3) Add two new fixtures under test/fixtures/: evidence-secret-leak-bearer-opaque.json (a DOM/screenshot captured_text containing `Authorization: Bearer gho_abcdef0123456789ABCDEF0123456789abcd` with NO dot structure) plus its `-ok` redacted negative-control companion, and evidence-not-secret-bearer-word-ok.json (ordinary text using the English word "bearer", e.g. "bearer of good news", that must survive to disk unmodified) — following the existing RED/OK pairing convention used for apikey/cardnumber/cookie in test/acceptance.test.mjs's F43/F44 test blocks. 4) Wire the new fixtures into the existing F43/F44 test bodies in test/acceptance.test.mjs (lines ~772-818) alongside the apikey/cardnumber/cookie assertions.

## 4. Systemic observations

- **Disclosure-debt pattern dominates this round.** 8 of 10 MAJOR findings are validity-envelope disclosure gaps (F60/F182 method-scope, patience-abandonment severity cap, F201 identity-drift matching, 3-persona grounding, single-rater reliability, ~45% agreement ceiling, F164/F108 test-coverage). The project's established remedy — append a new atomic F-line to the disclosure section, no behavior change — continues to be sufficient and should be applied uniformly rather than re-litigated per finding.
- **"Tested on one instance of an N-way rule" is a recurring test-coverage class.** F164 (1-of-10 flag pairs), F108 (presence-only, no order check), and F92/F165 (shape-only, no formula check) share the same root defect shape: the frozen suite proves a narrow special case, not the general rule the requirement text states.
