## 2. CONFIRMED defects

### BLOCKER

#### F49's ratified BLOCKED-counting formula contradicts F101/CR4-B2's own stated purpose — a 3-of-3 persona crash can read as clean CI
**IDs:** F49, F53, F101, F26, CR4-B2, scrub-log.md:CR4-closure-sweep-table
**Failure story:** F49's literal formula counts crashed/timed-out personas TOWARD the 3-persona floor, so a run where all 3 personas crash (zero findings) computes count=3, never sets BLOCKED, and F101 never fires CI-nonzero — exactly the "near-total persona failure reads as clean CI" scenario ADR-0001 and CR4-B2's own test rationale say must never happen. No fixture in the frozen suite exercises the crash-heavy quadrant.
**Fix directive:** 1) Invert the counted set for the BLOCKED trigger: BLOCKED := count(personas with run_status in {completed, patience-exhausted, runner-capped}) < 3 — i.e. crashed/timed-out personas count AGAINST the floor, not toward it (patience-exhausted/runner-capped are designed non-failure outcomes and should count toward avoiding BLOCKED; crashed/timed-out are the actual infra-failure signal BLOCKED exists to catch). Verify this still passes CR4-B2's negative control (1 completed + 2 patience-exhausted = 3 non-crash outcomes = NOT BLOCKED) and now correctly catches 3/3 crashed (0 non-crash outcomes = BLOCKED). Add the missing positive-control fixture `run-status-blocked-all-crashed.json` (3 personas, all run_status=crashed, zero findings) asserting the gate exits nonzero, and its negative-control sibling.

#### F49's BLOCKED formula computes the opposite of both of its own frozen fixtures
**IDs:** F49, requirements.txt:80, spec.md:201 (CR4-B2/CR5-B3), test/fixtures/run-status-not-blocked-patience-only.json, test/fixtures/run-status-blocked-with-disclosure-ok.json, test/acceptance.test.mjs:833-841, test/acceptance.test.mjs:820-830
**Failure story:** Applying F49's literal "fewer than 3 personas reach {completed, crashed, timed-out}" formula to the two fixtures written to canonicalize it produces the wrong answer in both directions at once: the patience-only fixture (1 completed, 2 patience-exhausted, count=1<3) computes BLOCKED=true but is ground-truthed "completed"; the crashed-present fixture (2 completed, 1 crashed, count=3) computes NOT-BLOCKED but is ground-truthed "BLOCKED". No literal reading of F49 satisfies both canonical fixtures simultaneously.
**Fix directive:** Rewrite F49 as: 'BLOCKED = true iff at least one persona subagent reaches run_status crashed or timed-out, AND fewer than 3 personas reach run_status completed (patience-exhausted and runner-capped count toward neither the crashed/timed-out trigger nor the completed floor).' Add a live-derivation test that computes run_status from a bare personas array (not a precomputed field) for both existing fixtures plus a third boundary case (e.g. 0 crashed/timed-out, 1 completed, 2 runner-capped) and asserts the formula's output matches the frozen ground truth in every case.

#### F159's frequency bucket and F162's persistence bucket are mathematically identical for every input — the "3-factor" severity rubric silently degrades to 2 factors with frequency double-weighted
**IDs:** F12, F159, F161, F162, F181, F184
**Failure story:** F159's frequency bucket and F162's persistence bucket (after substituting r=c−1) produce identical outputs for every possible within-run re-encounter count c, verified by direct enumeration — so F12's mean-of-3-factors formula is provably equivalent to round((2·frequency+impact)/3) for every finding, and a prior fix attempt (CR5-B4) shifting the input by 1 while also shifting the bucket boundaries by 1 was a mathematical no-op that never actually decorrelated the two factors. F181's disclosure understates this as mere "correlation" when it is guaranteed bit-for-bit identity by construction.
**Fix directive:** In .swe-spec/requirements.txt, amend F181 (line 281) to state the precise mathematical fact instead of the weaker "not independently verified" framing: Replace F181's text with: "F181: The validity-envelope disclosure section MUST state that, when severity_factors is stored as 3 numeric values, F162's default persistence bucket equals F159's default frequency bucket for every possible raw within-run re-encounter count, making persistence a deterministic duplicate of frequency rather than an independently verified NN/g input." Also update F12 (line 19) to append one clause disclosing the arithmetic consequence: append to F12's existing sentence "...when severity_factors is stored as 3 numeric values, the round(mean(...)) formula MUST be understood as equivalent to round((2×frequency+impact)/3) under F159/F162's default bucket mappings, since persistence duplicates frequency." Update the matching test regex in test/acceptance.test.mjs:292 (F181 test) to assert on the corrected disclosure text, and correct the stale scrub-log.md:253 / acceptance.test.mjs:276-281 comments that currently claim CR5-B4 "corrected" the double-counting — they should note the redefinition did not change the bucket-identity outcome, only the disclosure text does the real correction. Do not attempt to re-derive persistence from a genuinely independent signal in this pass — disclose honestly rather than engineer a fix at spec/pre-build phase.
