Of the 39 accepted: **12 mvp-critical**, **21 mvp-high**, **6 mvp-medium**. Zero were found to be already fully covered by an existing F/N line — every accepted item is a real, additive gap.

**The 5 most dangerous gaps found** (ranked by irreversibility × likelihood, given the MVP's stated mechanism: autonomous LLM-driven persona subagents live-crawling an operator-supplied real target app):

1. **No destructive-action denylist (DR-01).** Nothing stops a persona chasing "extra actions" (a mandated behavior, F10) from clicking a real "Delete Account" / "Cancel Subscription" button. This is the single highest-severity gap — real, irreversible data loss on a live app, and it is a *direct consequence of a feature the spec already requires*.
2. **No payment-mode gate (DR-02).** A happy-path list that includes checkout has no requirement stopping a real card submission against a misconfigured live Stripe key. Financial, irreversible, silent.
3. **No default dry-run boundary (DR-03).** This is the systemic root cause behind #1 and #2: nothing in the spec stops any non-idempotent POST/PUT/DELETE by default. A single wrong `--target` flag on day one turns every other gap live at once.
4. **No authorization/robots.txt gate (DR-04, DR-17).** The CLI as specified will happily fire N parallel real-browser sessions at any URL typed in, with no ownership confirmation and no `robots.txt` respect — an MIT OSS tool that is a ready-made unauthorized-scraping vector, with real legal exposure for the operator.
5. **No evidence/secret redaction (DR-05).** Screenshots and DOM snippets are mandated (F14/F15) but nothing redacts bearer tokens, cookies, JWTs, or card-like strings before they're written to disk — and those artifacts are explicitly meant to be committed/CI-uploaded. This is a live-credential-leak pipeline built into the MVP's core deliverable.

All five are `mvp-critical`, all five sit in the `side-effects` or `authz-privacy` lanes, and all five share one root pattern: **the spec defines what the tool should discover, but not what it must refuse to do.** See §5 for the full pattern discussion.

## 5. Cross-cutting observations

**Pattern 1 — "discover, don't refuse" is the dominant gap shape.** 7 of the 12 mvp-critical items (DR-01, DR-02, DR-03, DR-04, DR-05, DR-06, DR-09) are variants of the same root cause: the spec is thorough about what personas should *find and record*, and nearly silent about what they must *refuse to do*. The spec's own design intent — autonomous exploration, "extra actions" beyond the happy path (F10), open persona counts, live-target crawling — is exactly what makes refusal boundaries load-bearing rather than optional. This is not 39 unrelated gaps; it is one missing layer (a safety/refusal contract) surfacing 12+ times across lanes.

**Pattern 2 — the CI-mode promise (F26/N4) is under-specified at every layer it touches.** DR-06 (dedup), DR-08 (crash mid-run), DR-10 (run-completion status), DR-22 (baseline schema), DR-35 (finding_id) all trace back to one fact: CI mode diffs `findings.json` against a baseline and blocks on "new" severity-4 findings, but nothing defines what "new" or "same" means across a nondeterministic, parallel, LLM-driven pipeline. Landing DR-06 and DR-35 together (dedup rule + stable finding_id) unblocks the other three almost for free — recommend sequencing them first among the reproducibility/partial-runs cluster.

**Pattern 3 — "no ceiling" (D1) was a correct product decision that left its safety twin undone.** The founder explicitly removed the persona-count ceiling ("no ceiling; set open via data files"). That's fine as a product decision, but it was never paired with the operational controls an open-ended fan-out needs: concurrency cap (DR-38), per-persona action ceiling (DR-12), token/cost budget (DR-39), rate-limiting (V2-03, deferred). Three of these landed as accepted, one as v2 — worth flagging to the founder as a single decision ("open persona count" implies "the runner, not the operator, must own the cost/load ceiling") rather than four unrelated tickets.

**Pattern 4 — evidence capture (F14/F15) is the single highest-leverage integration point.** Three independent lanes (side-effects, authz-privacy, partial-runs) converge on the same two functions (screenshot capture, DOM snippet capture): DR-05 (secret redaction), DR-19 (third-party PII confirmation), DR-34 (gitignore instruction). All three are cheap to land together as one hardening pass on the evidence-capture module rather than three separate features.

**Pattern 5 — the rejected items share a tell: they propose new subsystems to solve problems the frozen spec already resolved by design.** Both rejections (§4) tried to reopen a decision (task-list ordering semantics, single blended score) that D2 or the ISO-score scrub already closed for a stated reason. Useful signal for future elicitation passes: when a candidate's own rationale requires inventing a new sub-schema or scoring engine, check the scrub-log and decision list *before* trusting the gap.

**Integration note for the landing agent:** every accepted line is written MUST/SHOULD and grep-ready for direct appending to `.swe-spec/requirements.txt` as the next free `F`/`N` number; keep the existing "one requirement per line" convention and preserve this doc's `DR-NN` id in a trailing comment (e.g. `F37: ... # DR-01`) so the delta is traceable back to this audit.
